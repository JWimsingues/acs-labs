= Exercise 6: Splunk integration
:navtitle: Exercise 6: Splunk integration

Estimated time: 15 minutes.

RHACS integrates with Splunk in two ways on this Showroom:

* *RHACS Technology Add-on (TA-stackrox)*: Splunk pulls violations and related data from the RHACS API on a schedule.
* *Native Splunk notifier*: RHACS pushes alerts to Splunk HEC when a policy fires.

You will inspect the add-on, configure (or reuse) the HEC notifier, trigger a violation, and search for the event.

== Task 6.1: Open the Splunk console

. On the bastion:
+
[source,bash]
----
oc get route splunk-web -n splunk -o jsonpath='https://{.spec.host}{"\n"}'
----
. Log in with user `admin` and password `RhacsSplunkDemo123!`.
. Go to *Apps* > *Manage Apps* and confirm *Red Hat Advanced Cluster Security* (`TA-stackrox`) is installed.

== Task 6.2: Check pull-based add-on data

. Open *Search & Reporting*.
. Run:
+
[source,text]
----
index=* sourcetype="stackrox-violations"
----
. If events exist, review fields such as policy, deployment, namespace, and severity.

NOTE: The add-on polls on a schedule. An empty result does not block the HEC push path below.

== Task 6.3: Configure the native Splunk HEC notifier

This cluster may already have a notifier named `Splunk SIEM (local)`.
If it exists and tests successfully, you may reuse it and skip create.

. Retrieve the HEC token:
+
[source,bash]
----
oc exec deploy/splunk -n splunk -c splunk -- \
  curl -sk -u admin:RhacsSplunkDemo123! \
  "https://localhost:8089/services/data/inputs/http?output_mode=json" 2>/dev/null \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('\n'.join(e['content']['token'] for e in d.get('entry',[]) if e.get('name')!='http'))"
----
. In RHACS, open *Platform Configuration* > *Integrations* > *Splunk*.
. Create integration `Lab - Splunk HEC` (or edit the existing local SIEM notifier) with:
+
[cols="1,2",options="header"]
|===
|Field |Value

|HTTP Event Collector URL
|`http://splunk.splunk.svc.cluster.local:8088`

|HTTP Event Collector token
|_(from the command above)_

|Source type
|`stackrox-alert`

|Skip TLS verify
|Enabled
|===
+
. Click *Test*, then *Save*.

TIP: The internal service URL works because Central and Splunk share the cluster.

== Task 6.4: Attach the notifier and trigger a violation

*Curl in Image* is disabled by default on this cluster. Use the enabled *Alpine Linux Package Manager (apk) in Image* policy instead.

. Open *Alpine Linux Package Manager (apk) in Image*.
. Edit the policy, open *Policy behavior*, attach `Lab - Splunk HEC` (or `Splunk SIEM (local)`), and save.
. On the bastion:
+
[source,bash]
----
oc run splunk-trigger --image=docker.io/library/alpine:3.18 -n frontend --command -- sleep 3600
----
. Wait about 30 to 60 seconds for image scan and policy evaluation.

== Task 6.5: Verify the alert in Splunk

. In Splunk Search, run:
+
[source,text]
----
index=* sourcetype="stackrox-alert"
----
. Open an event and confirm policy and deployment metadata.
. Optional comparison:
+
[cols="1,1,1",options="header"]
|===
|Source |Sourcetype |Mechanism

|TA-stackrox add-on
|`stackrox-violations`
|Pull (scheduled)

|Native Splunk notifier
|`stackrox-alert`
|Push (HEC)
|===

== Cleanup

[source,bash]
----
oc delete pod splunk-trigger -n frontend --ignore-not-found
----

. Detach the Splunk notifier from *Alpine Linux Package Manager (apk) in Image* if you attached it only for this lab.

== Key takeaways

* Pull (add-on) and push (HEC) can run together with different sourcetypes.
* HEC is the real-time path for SOC-style alerting.
* Always pick an *enabled* policy when you design a trigger step for students.
